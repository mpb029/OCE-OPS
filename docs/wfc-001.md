# WFC-001 — integrated Workface Control

Development base: `2cdc000af5fae87f2f343911e4491b1326784834`. Branch: `feature/wfc-001`. The owner subsequently authorised committing and deploying this build. Operational data, attachments and models must remain unchanged.

## Use

In Operations → Work Packages, Add/Edit the **original** package and select **Configure integrated Workface Control**. Record scope/location, structured metre chainages, activity, asset, planned dates and responsible person. Original progress, team, status, materials, prerequisite, constraint, photo and attachment controls remain authoritative. Configured workfaces cannot be silently downgraded to legacy readiness by clearing the configuration checkbox.

Expand **Workface Control** on a package to review its linked construction records and evidence. Link same-project records in the original form; optional **Require explicit task completion** uses the existing `done`/`wstatus=completed` semantics and excludes cancellation. Reference-only documents and photos are not automatically approval or completion evidence. Use explicit readiness checks for recorded hold points/actions; each satisfied check requires evidence.

Open **Permits & approvals** from Work Packages. One project-scoped approval can serve multiple workfaces. Create/save it in the register, then link its ID through each workface's Required applicability assessment. Record conditions, evidence and verified coverage for each workface. Coverage verification needs source, reviewer and date. Recheck the coverage checkbox after scope changes; the earlier verification is intentionally no longer sufficient. Removing an approval preserves linked files and leaves explicit missing-approval blockers until the workface links are corrected.

New approval details default to hidden from both Site and Client. Both the Work Packages display rules and the approval's explicit audience flags apply. A linked document/record must independently be visible in its original panel and selected project. Hidden approvals can still block readiness, with generic reasons only. These are display filters, **not access control**; a public repository does not provide confidential storage.

## Optional data extension

- `panels.workPackages[].workface`: version `1`; `description`, `location`, numeric/null `chainageStart`/`chainageEnd`, `activity`, `asset`, `responsible`, ISO date-only `plannedStart`/`plannedEnd`; `links[]` of `{category,panel,id,completionRequired}`; `checks[]` of `{id,title,responsible,due,satisfied,evidence}`; `permits` applicability `{assessment,ids,source,reviewer,date}`.
- Optional top-level `permits[]`: original UID convention, project ID, type, title/description, issuer, reference, source, responsible, recorded scope/restrictions/working windows, status, submitted/approval/effective/expiry dates, linked document ID, correspondence, reviewer, notes, explicit Site/Client flags, not-required assessment, `conditions[]` and `coverage[]`.
- `conditions[]`: stable ID, recorded wording, required/verified booleans, evidence, reviewer, date and optional due date.
- `coverage[]`: workface ID, verified boolean, source/reviewer/date, and a deterministic `scope` string tying the recorded verification to the approval/workface scope. It is evidence of what was reviewed, not a second Work Package or inferred geographic match. Associated workfaces are derived from their permit links; no second association store is created.

Unknown fields are retained on edited workface, applicability, link, check, approval, document, assessment, condition and coverage objects. Unconfigured records acquire no `workface` field on render/open/cancel. The existing full-state save/export/import/publishing paths carry the optional register; shared refresh explicitly replaces/removes it with the received state. Strict import validation runs before mutation. Invalid references must be corrected before publishing or importing a backup; an exported backup still retains them for recovery/repair.

## Readiness rules

Legacy packages keep materials/prerequisite readiness and show **Workface / permit assessment: Not assessed**. Configured workfaces combine those original gates with validated workface/approval structures. No editable GO flag is stored.

NO GO results from unassessed applicability; absent, invalid, cross-project or ambiguous references; an unsubstantiated not-required assessment; unlinked required approvals; pending/rejected/suspended/revoked/expired approvals; missing recorded approval authority/source/reference; missing/future effective or approval dates; expiry before today or the recorded planned dates; unverified/stale scope coverage; chainages outside recorded coverage; required conditions without verified evidence; incomplete explicitly required linked tasks; or unsatisfied explicit checks. Future-dated verification cannot satisfy a gate.

Date-only validity uses **Australia/Brisbane**, inclusively through the expiry date. The compact lookahead is **14 calendar days**, an informational display threshold, not a statutory deadline. Open pages refresh their readiness after the Queensland date changes, once no form is open. Print always derives current readiness. Free-text constraints alone remain notes and never change GO/NO GO.

Coverage, activity restrictions and working-window wording require recorded human verification. There is no geographic guessing, automatic interpretation of permit prose or intraday authorisation engine. **GO is a derived planning indicator, not regulatory, engineering or safety authorisation.** Source/authority requirements must be established independently by the responsible project team.

## Implementation and verification

`workface-data.js` contains pure validation/readiness/date functions. `workface-control.js` uses a small explicit adapter in `index.html`; it never duplicates Work Package CRUD or owns a second store. `workface-control.css` is scoped to these controls. The eight workspaces, 21 panels and Leaflet/Three instances remain unchanged. The original single Work Package native print sheet adds scope, approvals, conditions, linked references and blockers using current audience filters; it does not embed external approval documents.

```sh
node --test tests/workface-data.test.cjs

# repeat the focused command with OCE_ENGINE=firefox (unset OCE_BROWSER)
```

The standalone runner reuses the existing harness. All fixtures are synthetic and GitHub writes are intercepted. `OCE_WFC_FILTER` selects an individual contract when correcting a demonstrated failure. Results include source hashes, browser/version and operational-data preservation. No FULL suite, PDF package, screenshot gallery or recovery archive is needed for this intermediate build. Existing STAT-001/NAV-001 assertions and verification infrastructure are unchanged.

Owner acceptance remains: use actual project approval evidence to review terminology/coverage decisions; check the original workface and new approval forms on the physical Android tablet (keyboard, scrolling, Save/Cancel); review a native printed sheet. Browser touch emulation is not physical-device or printer acceptance. No regulatory applicability/authority defaults are inferred from selectable categories.
