## Site access and use

1. Open the existing Site dashboard using its current complete `?crew=<siteKey>` link. **Site Diary** is directly in the dashboard header; no office dashboard navigation is required. The same tool is available in the unlocked editor. Client, invalid/blank Site links and the locked editor cannot open it.
2. Create/unlock the private diary vault with a device passphrase of at least 12 characters. This is local encryption, **not authenticated project access**. Keep the passphrase safely; it cannot be recovered. A separate handoff passphrase protects each exported file.
3. Select **New diary**, select the project, and record the date, shift, work area, preparer and supervisor. Dates default to Australia/Brisbane; an explicitly configured project `timezone` is respected. Multiple shifts/crews/areas can have separate stable-ID diaries for the same day. Today's diaries filters the saved register rather than silently creating duplicates. A saved diary's project is immutable.
4. Use Work completed, Labour & plant, Conditions, Delays & instructions, Photos & files, and Review / handoff. Select original Scheduled Works to prefill recorded planned scope, workface, location, chainages, quantity and unit. Actual work/quantities remain blank until entered. Unplanned work is explicit.
5. **Save draft on this device** accepts incomplete preparation. Changes also autosave after an idle interval; successful feedback appears only after the IndexedDB transaction completes. Refresh and unlock to continue. Back/Escape preserves a dirty draft before closing; failed saving keeps the form open. An unsaved/in-flight page has a browser unload warning.
6. Check & mark ready validates the required identification and activity account. **Prepare encrypted office handoff** downloads an `.oce-diary` file and records **Pending transfer**, never Submitted. Retain the file and send it using an approved private channel, with its passphrase separately. No transmission or office synchronisation occurs in the app.
7. The office opens Site Diary in the unlocked existing editor and imports the file. **Received** is acknowledged only after the private local import commits. It means manual local receipt, not an authenticated server acknowledgement. Filter by project/date/workface, inspect the original entries/photos, record review, return for correction, or print. Receiver/reviewer identities are labelled self-declared.
8. For corrections, export the office return file, import it on the originating field device, and select Start correction revision with a reason. The subsequent handoff links to the previously received hash. Exact retries do not duplicate diaries; newer/conflicting forks are rejected rather than overwritten. Previous received/reviewed content remains in revision snapshots.

## Security gate and future adapter

Inspection found no genuinely authenticated Site writing service. The static page uses display filters, an editor casual password gate and browser-held GitHub credentials for editor publication. Even the existing Site key is present in publicly retrievable board data. Neither a Site link nor a local vault unlock authenticates a person or enforces server-side project permissions.

WFC-004 therefore has **no remote Submit implementation**, embedded token, anonymous endpoint, new backend or external service. It never calls the GitHub file-upload or board-publish transports for diary capture. `Submitted` is reserved in the state vocabulary; no production code path can manufacture a successful remote submission. Mocked/file tests are not claimed as authenticated delivery.

Minimal separately approvable next step: an HTTPS submission adapter behind the organisation's managed identity provider, a private record database and private object storage. The service must enforce project membership/roles for every record and file; accept stable diary ID + revision + payload hash/idempotency key; reject stale/conflicting revisions; retain immutable history; and return a durable receipt bound to that exact ID/revision/hash. Retries must retrieve the same receipt. Private file access needs authorised short-lived reads. An office inbox must read that destination and acknowledge durable receipt. Only a verified response from this authorised service may advance Submitted/Received remotely. Do not connect this to public `data.json` or distribute administrator GitHub tokens to field users. No provider, account or expenditure was introduced or approved here.

Local AES-GCM encryption protects locked stored/exported diary contents from casual same-origin Client-page inspection. It is not remote authorisation, a tamper-proof audit/signature, protection against a compromised unlocked app/device, or a replacement for OS/device security. Private diary reports/files must use approved private handoff channels. Original photographs can contain their own EXIF metadata; the app neither extracts precise locations nor strips/recompresses the original files.

## Data contract and storage

One authoritative private diary register lives in `oce-ops-private-diaries-v1` IndexedDB, namespaced by the existing repository identity. `vaults` contains salt, a cryptographic unlock check and random local device ID; `diaries` contains encrypted records and CAS storage revisions; `attachments` contains separately encrypted original bytes. Non-extractable AES-256-GCM keys are derived with PBKDF2-SHA256, 210,000 iterations and a random salt. Every encrypted payload uses a fresh nonce. Keys stay in page memory and are dropped on lock/context loss. There are no image blobs or diary records in localStorage.

Private record version 1:

- Stable `id`, `project`, `date`, `shift`, `area`, `preparedBy`, `supervisor`, created/modified timestamps, revision, lifecycle status, originating device, immutable history; optional recovery-owner and handoff lineage references.
- `activities[]`: stable entry IDs; original workface/scheduled-activity IDs; planned/unplanned kind; description/location/chainage; recorded planned work, actual-work account, planned/reported quantity and unit, status/times/notes, existing constraint and evidence references. No verified quantity or QA acceptance is inferred.
- `labour[]`: crew, trade, personnel count, hours/basis, existing subcontractor reference, activity allocation, subcontractor/work description and notes. No required individual personal information or payroll.
- `plant[]`: existing equipment reference, recorded type/ID, activity allocation, operating/standby/downtime hours, reason and notes. These are not approved hire charges.
- `weather`: explicit observed/reference basis, optional recorded rainfall/temperature and ground/water/workability/access/environment/interruptions text. No automatic measurements.
- `interruptions[]`: affected activity/resources, category, recorded times/duration, observed event, alleged cause, effect, mitigation, follow-up, existing constraint/RFI/issue/document references, evidence notes and unassessed commercial implications.
- `instructions[]`: source, recorded date/time, verbal/written distinction, related original correspondence, description/action/follow-up. No contractual approval is inferred.
- `attachments[]`: original OCE-style name/MIME/size metadata, stable local attachment ID or original permitted record/path reference, caption, diary activity, location/chainage note and optional recorded time. Compatible unknown record/nested fields are retained on edit/handoff.

Local limits: 100 diaries; 100 MB per repository vault; 50 MB of original file bytes per diary; 2 MB diary text/history; 200 entries per section; 500 history events; existing per-file limits of 15 MB/photo and 25 MB/other file. Quota errors never show success or delete an earlier saved copy. Private record and new-file writes/deletions are atomic. Removed local files are deleted only when no current/historical diary reference needs them; shared repository files are never deleted. No automatic archive/purge is performed.

The encrypted handoff has an explicit format/version, fixed KDF parameters, random salt/nonce, authenticated ciphertext, purpose (handoff/recovery/review), complete original local file bytes and a payload hash. Unknown compatible diary fields survive. Missing/duplicate/unreferenced files, inconsistent byte sizes, altered existing attachment IDs/bytes, invalid structures and cross-project references are rejected before receipt. Imported identity/history claims are not treated as authenticated.

Recovery export can preserve invalid in-memory draft input for repair when normal saving/validation fails; it cannot masquerade as a validated handoff. Restore/receipt still validates before installing anything. A valid recovery file can restore a private draft on another device; it never invents submission/office receipt. Keep encrypted exports outside the browser to survive browser-data clearance or device loss. A forgotten vault/file passphrase cannot be recovered.

## Integration with original operational records

The diary is intentionally absent from `state`, `data.json`, board backups, publishing payloads and the WFC-002 editor journal. Existing board data has no migration. Original panels, IDs, forms, workflows, models and map/Three instances are retained. Source pickers/reference resolution use current project and original audience/panel/item/retirement rules. Client views cannot unlock/render diary contents. Previously recorded private diary text/history is retained as evidence, rather than rewritten from a changing source register.

After explicit office review, **Adopt reported quantity to Daily Works** requires a public-safe description, recorded adopter and an explicit disclosure checkbox. Only that description, work date, quantity/unit and stable source IDs enter one original Daily Works allocation through WFC-002 guarded atomic save. It is an unpublished draft; Publish stays separate. Optional `allocation.diarySource` records diary/entry IDs, adopted revision, adopter/time and a fingerprint. No private diary payload, labour, instructions or photos are copied. Default Site/Client flags are false; the warning explains that the repository itself is public.

The original WFC-003 progress function aggregates these existing allocation increments and derives remaining quantity against an established plan/unit. A source-entry/revision retry is idempotent. An explicit later reviewed correction updates the same allocation ID, not a second increment; manual changes/cancellation of that allocation block automatic replacement. An intervening board change is rejected inside the original WFC-002 save queue using optional `expectedBoard`. Drafts cannot adopt. Deleted diary entries do not silently delete/cancel previously adopted Daily Works: correct that original record explicitly. QA acceptance, Work Package completion, permits, coverage, readiness and frozen weekly/PPC outcomes are untouched.

**Open original proposed-constraint form** reuses WFC-003's existing form, project, activity/workface IDs, a checked public-safe summary and a diary provenance reference. The original Save is still required. Diary text never creates/closes a constraint or changes formal approval/readiness automatically.

Print uses the original logo/header, scoped image preload and native print mechanism with a private A4 sheet. It includes original diary accounts, quantities/allocations, labour/plant, conditions, delays/instructions, action notes, photo/file index and explicit preparation/receipt/review status. Supporting documents are references, not merged PDFs. Public board/Client reports do not incorporate private diary sheets.

## Remaining acceptance and limits

Remote submission/authenticated identity/private server file access remain **BLOCKED pending separate architecture approval**. No successful local or mocked result removes that blocker. There is no unattended office sync, authenticated signature or server-enforced project permission in this build.

On the physical Samsung/Android tablet, the owner must check camera/gallery selection, portrait/landscape scrolling, outdoor legibility, IME/Save/Back behaviour, local save + refresh/unlock, and encrypted file transfer/import. Desktop native printer/PDF-dialog selection and a real private office handoff also remain manual acceptance. Browser touch emulation/reduced viewport is not hardware acceptance.

Offline entry works once the application is loaded; a cold offline start is not guaranteed. Existing CDN availability limitations remain as recorded in `wfc-003-cdn-reliability.md`. Browser quota/private-mode/storage clearance can prevent or remove local saves; explicit errors and separately retained encrypted files are the recovery path. There is no automatic archive, cloud backup, conflict-fork merge or silent deletion of an adopted progress record. STAT-001/NAV-001 remain unchanged.
